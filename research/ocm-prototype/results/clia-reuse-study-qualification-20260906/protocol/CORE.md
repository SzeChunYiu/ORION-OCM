# Executable reuse: prospective development panel

Owner [#62](https://github.com/SzeChunYiu/ORION-OCM/issues/62#issuecomment-5556647228);
anchors #69/#73/#50; roadmap #42/#46–#47; acceptance #38/#49. SUPPORTING.

**No panel has run.** This draft requires final source and acquired-object bindings.
Use [protocol.json](protocol.json), [public requests](public-requests.jsonl) and
[external grading](GRADING.md). Source-review qualifications are in [REVIEW.md](REVIEW.md).

The smallest useful panel is 36 new-tuple applications per arm: 12 initial reuse,
12 after restart, then four each after historical-provenance withdrawal, real
authority withdrawal and restoration. Two applications should be policy refusals;
34 should return independently correct integers. Five actual syntax queries
repeat one public sentence to check retention; syntax is structure-only here.

Each arm independently acquires max3 and guard2 once using the same cvc5/grammar/
universal checker contract. Retain both acquisition receipts and all costs.
The native parent receives the same conventional callable/cache/check/support
powers. If canonical programs differ, report CANNOT_CHECK_IDENTICAL_DONOR_BINDING;
do not select either program or call that a capability failure.

F0 binds final source/checkers, model, tasks, tuple/phase plan and resource envelope
before acquisition. F1 then binds each arm's actual descriptor, program, assumption
support and history IDs before any application. The public templates contain only
requests, with @max3/@guard2 aliases replaced by those F1 IDs. Neither arm receives
the grader or expected answers. Acquisition processes exit at F1; initial reuse
therefore includes a fresh-process bind. Its first call is cold, not warmed for free.

Exactly six actor OS processes run per arm, in this order:

| Stage | End-of-stage action, then audit/persist/exit |
|---|---|
| acquire | Export F1 identities; no revision |
| warm | No revision |
| restart | Withdraw max3 search history |
| history | Withdraw max3 query-registration authority |
| withdraw | Restore the same registration authority; keep history withdrawn |
| restore | No revision |

Every next stage audits the reloaded state before rebinding and querying. No
extra modifier actor processes are planned. Creating a new runtime object within
the same process is not a restart; solver/checker children remain fully charged.

Withdraw max3's actual search-history record first. This is historical information,
not a proof premise, so authorization and prior commitments should remain live.
Then withdraw only the actual max3 query-registration assumption, persist, restart
and refuse new max3 use while retaining guard2 and syntax. Audit existing max3
outputs' current authority too. Restore the same registration IDs while leaving
history withdrawn; require exact descriptor/program recovery and old-output revival.
No query re-registration, reacquisition or new authority assumption may repair refusal.

This withdraws authority to reuse under the declared specification. It does not
make a correct integer false, delete historical bytes or establish neural unlearning.
A conventional library may explain all reuse savings: PARENT_SUFFICIENT is valid.
Two known functions with new inputs do not establish transfer to new synthesis
families, meaningful LLM comparability, learning-to-learn, sparse cognition or an
OCM-specific efficiency advantage.
Report exact stale acceptance, collateral/current-authority outcomes and a
descriptive resource vector. This control defines no state-size dominance or
locality-scaling decision rule and does not adjudicate those terminals.
