# Aggregate controller and offline evaluator profile

Current source authority: [exit-code successor](resource-exitcode-records/CORE.md),
qualified on 23 source files with 12/12 profile cases and 65/65 focused controls.
The original 19-source and [prior 22-source](RESOURCE-SUCCESSOR.md) qualifications
remain historical; neither receipt authorizes the changed current runner bytes.

This component supervises registered evaluator build/export commands. It does
not select corpus rows, propose proofs, grant kernel authority or certify a
whole host free of neural computation. All workload execution is on billy-laptop.

## Entrypoints

- Trusted file entry: `python -I -S resource_boot.py run --profile P.json
  --limits L.json --output NEW_DIR`. Parent integration must source-load this
  bootstrap, then call `resource_boot.load()["build_profile"]`. Ordinary imports
  do not establish loaded-byte custody and direct unstamped dispatch refuses.
- `build_profile.run(profile, limits, create_only_output)`: validates the exact
  source/code profile, loads one owned AppArmor policy, runs the command under
  three v1 aggregate controllers and a fresh bwrap namespace, checks input/source
  custody again, and retains the receipt and raw process streams.
- `resource_runner.run(argv, env, limits, create_only_output, owned_paths)`:
  lower-level controller supervisor; **does not itself provide offline isolation**.
  Acquisition or other uses require their own registered profile.
- `python -I -S resource_boot.py install --output <new-dir>`: installs only the two protected helper
  modules under `/usr/local/libexec/ocm-f1-coverage-v1`, preserves predecessors and
  command outputs, and refuses installation while an owned controller is active.
  No existing runner/service/cgroup configuration is changed.

## Exact profile contract

`schema = ocm.f1.build-profile.v1`; no extra top-level fields:

| Field | Value |
|---|---|
| bwrap, aa_exec | canonical file record: path, SHA256, bytes |
| files | list of {source: file record, guest, access} |
| access | executable, library, or read |
| materials | list of {path, guest, inventory: file record} |
| writable | list of {path, guest}; separately owned artifact directories |
| argv | strings; argv[0] must be an explicitly registered executable |
| environment | explicit PATH/HOME/TMPDIR/LEAN_SYSROOT/LEAN_PATH/LEAN_NUM_THREADS/LANG/LC_ALL/TZ |
| code_audit | bound external audit JSON |

Material inventories are generated by `build_profile_policy.inventory(path)`.
They enumerate all regular files with hash/bytes, directories, and internal
symlinks with their exact target. Escaping symlinks/special files refuse. This is
file custody, not a Lean import or semantic-dependency certificate. Immutable
materials may contain Lean source, public/private/server/IR metadata and headers.
They do not automatically grant executable file mapping.

Each executable, loader, shared library and native plugin gets its own file
mount and permission. Source/material directory mounts are read-only. Writable
artifact guest directories may overlay a material subdirectory; their host paths
must be separate from every input tree, and they cannot cover registered code.
Supervisor receipt roots may not overlap any writable or input path. Unsafe
output paths refuse before mkdir; the caller records that pre-dispatch refusal.
Whole /usr, /home, /etc, /var, /run or /tmp material roots are refused.

The audit schema is `ocm.f1.build-code-audit.v1`, with exactly:
`profile_payload_sha256` (SHA256 of canonical profile excluding code_audit),
`non_neural_code_reviewed: true`,
`dynamic_code_scope: REGISTERED_EXEC_AND_FILE_MAPPING_ONLY`,
nonempty bound `evidence`, and textual `limitations`.
Canonical JSON is sorted, compact, finite, UTF-8, with one final newline.
The audit is externally reviewed authority. Checking its shape/hash does **not**
prove the review, completeness of library closure or absence of neural code.
Source/interpreted code, scripts, compiler plugins and generated-code admission
must be covered by that review. New native plugins in writable outputs cannot
execute/map until a separately recorded admission binds them in a new profile.
Network denial alone never establishes the no-neural requirement.

## Resource and isolation scope

Limits have the exact keys validated by `resource_contract.validate_limits`.
The registrar must bind the prospective envelope in F1-CORPUS-COVERAGE-EXECUTION;
smaller settings are accepted for explicitly authored qualification.
The current profile uses memory and combined memory+swap v1 limits, cpu/cpuacct
CFS quota, and pids.max. Limits remain root-owned; only cgroup.procs is delegated.
The child joins all three groups before exec; build descendants inherit them.
The Python supervisor/setup/custody work stays outside workload groups. Its wall
cost is recorded; group memory peaks are not aggregate host RSS or supervisor RSS.

bwrap receives an empty host environment and only explicit --setenv additions.
It unshares supported namespaces (including network and PIDs), drops capabilities,
uses --die-with-parent, and mounts only registered files/materials/artifacts plus
fresh proc/dev/tmp. The installed older bwrap lacks --clearenv; env={} supplies
that boundary before bwrap starts. AppArmor additionally denies network and grants
execute/mapping only to the registered file paths. Writable artifacts lack x/m.
The policy permits scoped proc reads, null/random device use and signal handling.
This is a fixed allowed-code profile, not a sandbox for arbitrary adversarial
Python callbacks or proof of semantic properties of the permitted program.

The monitor counts logical owned bytes and allocated bytes separately, samples
free space, and spools stdout/stderr directly to files. Sampling/scan time,
first stop, final bytes, overshoot and cleanup delay remain visible. This is a
sampled stop, **not a hard aggregate disk quota**; scanning plus polling and
termination allow overshoot. RLIMIT_FSIZE is the inherited per-file bound.
Disk scans deduplicate overlapping owned roots. Profile metadata and artifacts
are included; acquisition and cold source storage need the registrar's own cost
ledger. Final receipt bytes are written after the last disk sample.
Unreadable/failed disk scans are unavailable evidence, never zero bytes; cleanup
and receipt capture still run, and unavailable overshoot is null. Signal handlers
are restored even if the final receipt write itself fails.
PID-safe signalling uses native wrappers or qualified Linux x86_64 pidfd syscalls;
there is no bare-PID kill fallback. Catchable host interruption retains a receipt.
SIGKILL/power loss may leave incomplete evidence and require scoped recovery;
they are never silently reported as success.

## Receipts and operational qualification

Resource terminals: COMPLETED, COMMAND_FAILED, RESOURCE_STOP, SETUP_REFUSED,
INTERRUPTED or CLEANUP_INCOMPLETE. The profile adds PROFILE_REFUSED for invalid/
changed input or profile preparation failure. Mapping these to row-stage
CANNOT_CHECK/NOT_RUN is the registrar's job; a resource stop is not proof rejection.
Raw stdout/stderr/samples, exact argv/environment, controller readback/statistics,
actual loaded-source stamps, policy and cleanup records are retained. The trusted
bootstrap compiles owned source bytes; the root helper independently compiles its
contract bytes. Matching-header stale caches are covered by paired controls. Incomplete cleanup
retains its AppArmor policy; the root helper also refuses unloading a policy
whose owned controller remains populated.

Focused tests require no corpus/Lean execution. Privileged live controller tests
are enabled only by `OCM_RESOURCE_HOST_QUALIFICATION=1`; ordinary portable runs
skip those explicitly. See RESOURCE-QUALIFICATION.md for observed evidence and
final source qualification status. Do not infer permission to run corpus rows
from these authored controls.
