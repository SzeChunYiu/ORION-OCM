# Checked unary methods in the actual OCM runtime

This is an authored engineering slice: mechanically acquired data survives an actual
process exit and is used by one registered dispatcher inside OCMRuntime.solve.
It is not a registered scientific assay, learned utility result, broad language transfer,
or a comparison establishing improvement over the equally adaptive symbolic parent.

## API and source boundary

- MethodStore(runtime, create=True) declares separate semantic, schema-checking and
  answer-checking assumptions. acquire(checked_training) invokes the existing proper
  subcover miner and independent universal-schema checker; no target rule is supplied.
- MethodStore(runtime) restores the actual KSO ledger and the separate issuer ledger.
  read(method_id) checks exact rule/envelope/anchor/edge/evidence/source identities.
- MethodIndex visits issued entries, then uses conclusion-kind postings. It validates
  the current field, revocation, nogood and issuer state before reuse.
- MethodRuntime(store).solve(task, invoke=True) admits an exact conditional request,
  calls actual OCMRuntime.solve, and journals a packet only after committed checking.
- unary_method_episode.py acquire|solve request.json result.json is an authored
  CPU process entry. Process B's input has task/invoke/store only; it contains no
  training examples, supplied rule, code field or callback restoration instruction.
- unary_method_process.launch(..., profile=None) records the exact -I -S -B command, interpreter,
  request, sources, raw output, start/end, exit, child CPU, PID and cleanup.

All persisted method/task/candidate payloads are bounded canonical plain JSON.
Metadata strings are checked as exact built-in types before canonicalization.
The rule grammar, semantic checker, matcher and exact cached region parent are shared.
Source bindings cover the current OCM/orion_v2 Python tree, unary rule/method modules
and four semantic modules. This is an explicit conservative source set, not a claim
that every hashed source was imported or every host file was isolated.

## Explicit interpreter profile

The launcher profile has exactly schema, executable, sha256 and version fields,
with schema ocm.unary-method.python.v1, a resolved absolute executable and exact
Python 3.11.14. The default retains the previously recorded laptop binary SHA.
observe() describes the current interpreter for explicit engineering test configuration.
That observation is not a scientific or host qualification; an assay must separately
seal its selected profile before execution. No task or method field sets this profile.
The parent verifies the selected file before dispatch and passes canonical profile
JSON through its fixed bootstrap environment. The child checks its actual executable,
SHA, version and isolation flags. Both records bind the profile and postcheck the file.
No arbitrary entrypoint, import-root, callback or extra environment field is accepted.

## Actual invocation and proof authority

The generic registry declaration has stable empty input_atoms and a source-hash
version. Each SV wrapper supplies its current request atom. Before dispatch the bridge
requires the exact registered callback object; registry fingerprints do not hash code.
OCM's existing callback guard protects API-mediated field mutations during the solve.

The backend prepares premises once, indexes candidate rule data, structurally matches
Boolean substitutions, and constructs the existing cover certificate. A miss or
disabled invocation completes the same prepared exact parent. The method ID names
an actually attempted/used data rule; it is not another selected OCM operator.
The final checker closes over the original admitted request, checks the exact issued
packet bytes, rechecks the current method and support substitution, then invokes the
independent direct-semantics answer verifier. No query solve precedes method matching.

A method's mathematical warrant derives from semantic and schema-checker assumptions.
Discovery evidence and the authored selection policy are separate. Removing discovery
does not invalidate the independently checked rule. Removing utility disables this
selection policy; it is not a mathematical refutation. Removing the schema environment
disables methods but permits the independently checked exact parent when semantic
and answer-checker assumptions remain live. UNKNOWN method liveness refuses reuse.
UNKNOWN query answers and inconsistent premise sets can have valid checked certificates.

Answer authority derives from the conditional request plus semantic/answer-checker
assumptions. The independent answer verifier supplies the current answer check;
a claimed method ID never automatically augments candidate warrant. These answers
assert conditional entailment under the supplied premises, not external world facts.

## Persistence, revision and failure

A method issuance writes PREPARE, admits one atomic KSO batch, then writes ISSUE.
The two ledgers are not one transaction. A pending issuance causes cold restore to
refuse even if its KSO atoms exist. An unissued EXACT_CHECKER atom is not a method.
Proof-channel labels and matching hashes are never used instead of schema checking.

USE_PREPARE is written before dispatch. USE or USE_REFUSED finishes the intent;
a pending use causes cold restore to refuse, including after a core checker pass.
A successful USE record preserves the request, complete checked packet/trace and exact five-event
core interval: query opening, navigation, extraction, composition and checker result.
Cold restore checks those hashes and actual KSO/evidence identities, then independently
verifies the archived answer and binding without solving or rebinding callbacks.
This recheck establishes historical checked content; current liveness/selection is
separately evaluated. Reinstatement enables a fresh match and check, not automatic
reuse of a prior answer. Removing an actually used premise invalidates that binding;
legitimate alternative bindings remain allowed.

Hash chains and byte bindings operate under the existing trusted host/filesystem
and checked issuer implementation. They do not authenticate an adversary who can
rewrite all ledgers, source and receipts. A core commitment followed by a failed USE
append does not establish durable recorded use, and no cross-ledger atomicity is claimed.

## Accounting and execution scope

Telemetry includes candidate IDs/attempts, actual recipes, index visits/probes/postings,
matching/schema/key/subset work, parent semantic totals and cumulative full-prepared
binding work. Preparation is charged once; complete is invoked only on actual fallback.
All method reads deliberately recheck the registered source set and may scan evidence
history; those reads, hashing bytes, schema checks and journal bytes are counted.
No sparse-execution claim follows from the small rule index. Core navigation/admission,
whole-ledger rewriting and replay remain real work.

Refused matching retains known preparation/index/attempt observations and explicitly
marks unavailable partial matcher counters; no zero-work inference is made.
The inner solve_wall_s covers request admission, intent, index, OCM execution and checking
through core return. It excludes the subsequent USE validation/append. A separate return_observation
records journal wall and total wall after append, outside the self-bound journal
receipt. Child-dispatch/wait wall and waited child CPU include the child
work, persistence, imports and child source custody. The launcher outer_wall_s covers profile verification and child dispatch/wait. It starts
after its initial source scan and stops before its final source scan/raw validation
and PROCESS write; it is not the whole launcher call. The encompassing pytest
process observation includes that launcher work. No nested durations are added.
Store work is cumulative within the process. Logical counters exclude Python allocation,
serialization/hash implementation cost and many core internals; wall/CPU observations have the
explicit spans above, not sums of overlapping nested times.

The process entry records actual import origins and hashes, refuses undeclared or
site-package origins and existing cached project bytecode, and verifies its explicitly selected
interpreter profile/flags. It explicitly reads the runtime's host-callback registry count for
the before-rebind observation; it does not mutate core private state.
-I/-S and these observations are not filesystem, network or arbitrary-Python containment.
The authored path invokes no neural model or external service; qualification of a
future scientific launch profile and the equally adaptive conventional store arm
remain separate work. Existing semantic/learning receipts remain historical.
