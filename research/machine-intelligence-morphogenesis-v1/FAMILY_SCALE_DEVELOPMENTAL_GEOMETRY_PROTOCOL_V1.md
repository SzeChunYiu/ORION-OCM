# Family-scale developmental-geometry protocol v1

Status: **design/protocol only. No protected outcome.**

Purpose: replace weak `can a universal basis represent a tiny example?` tests with a cross-paradigm assay of developmental geometry, acquisition cost and phase predictions.

## 1. Scientific question

> When several morphology families have enough expressivity for the registered task family, can measurable properties of their developmental geometry predict which family reaches matched verified capability with lower complete acquisition/lifetime burden as task ecology changes?

This is stronger than architecture benchmarking because the prediction must be derived and frozen before protected outcomes.

## 2. Parent kill gate

Before execution, reconstruct at minimum:

```text
algorithm selection / portfolios
resource-rational analysis
meta-learning / learned priors
AutoML/NAS
online experts / switching regret
native learning theory for every chosen family
```

If the experiment only chooses the best from a supplied portfolio using task features, terminal:

`ALGORITHM_SELECTION_PARENT_SUFFICIENT`.

## 3. Family selection

Use at least four developmentally different parent families with mature implementations/theory. Candidate first finite/synthetic set:

### N — differentiable parametric

A small finite-precision linear/MLP family with registered SGD/optimizer update.

### S — symbolic/rule

Decision-list / production-rule / ILP-like bounded family with exact rule-search/induction parent.

### P — probabilistic

Small Bayesian/factor/generative model with exact or bounded-enumeration inference.

### G — programmatic/library

Typed program grammar with enumerative/CEGIS/library-search parent.

Optional later:

```text
reservoir/readout
VSA/HDC
OCM-like explicit search-capital morphology
hybrid parent product
```

No family is weakened to make the theory look right.

## 4. Critical separation: architecture versus learned prior

For each family evaluate at least:

```text
RAW       architecture/family with neutral standard prior
ADAPTED   same family after matched meta-training/development on development ecologies
RESET     same family without prior developmental history
```

This tests whether the phase belongs to architecture or to an acquired prior/geometry.

## 5. Ecology axes

Choose axes where parent theory gives directional predictions. Do not invent them post hoc.

First candidate factorial ecology:

```text
A. compositional/algorithmic regularity: low vs high
B. observation noise: low vs high
C. partial feedback granularity: dense vs sparse/block-level
D. reuse horizon: short vs long
E. revision/drift frequency: low vs high
F. verifier strength/cost: weak/noisy vs exact/cheap
```

Start with 2–3 axes in one registered experiment; do not explode into an unfalsifiable grid.

## 6. Developmental-geometry pre-measurements

Before protected target success, measure per family:

```text
candidate/proposal rank of eventual successful structure where identifiable
useful-descendant mass or empirical improvement rate
update locality / parameters-rules-program nodes touched
credit-assignment depth
accepted/rejected proposal count
verification calls
representation/library changes
retention after each update
training/meta-training state size
```

These are candidate mediators. Final accuracy alone is insufficient.

## 7. Complete resource vector

At matched capability record:

```text
prior/meta-training cost
new target examples/information
candidate/search work
forward/inference work
backward/update work
verification/checker work
persistent bytes
active bytes
communication/message work
revision/retraining work
maintenance/index/library work
wall/CPU/GPU where available
```

No architecture is allowed free pretraining or free hand-authored structure.

## 8. Prospective phase prediction

Before protected runs, freeze a matrix of the form:

```text
regime R1 -> family/equivalence class expected on frontier
regime R2 -> another family expected on frontier
regime R0 -> no meaningful difference / parent tie
```

Predictions must include at least one parent-favoring/no-transition region.

A useful statement names a quantitative mediator, e.g.:

```text
sparse block feedback lowers useful-descendant mass of local-update geometry
below chunk/program geometry by registered ratio/bound;
long reuse horizon then amortizes its larger acquisition cost.
```

## 9. Search-independent frontier versus discovery

Separate two tests:

### F — frontier test

Given faithful trained/tuned parent instances, estimate the actual developmental Pareto frontier.

### G — generation/search test

Starting from a common neutral meta-generator where feasible, ask whether it discovers the predicted family/geometry under the registered development budget.

A correct frontier with failed search is:

`MORPHOGENESIS_SEARCH_FAILURE`, not failed phase theory.

## 10. Required arms

At minimum:

```text
native strongest family learner
matched universal/program implementation where meaningful
meta-trained/adapted version
reset version
strong hybrid parent product
```

For OCM later:

```text
CONTINUED_OCM
RESET_OCM
same donors + ordinary memory/search parent
```

## 11. Negative terminals

```text
ARCHITECTURE_DIFFERENCE_VANISHES_AFTER_META_LEARNING_AT_SCOPE
ALGORITHM_SELECTION_PARENT_SUFFICIENT
RESOURCE_RATIONAL_PARENT_SUFFICIENT
HYBRID_PARENT_PRODUCT_DOMINATES
PHASE_PREDICTION_FALSIFIED
NO_MEASURABLE_GEOMETRY_MEDIATOR
ACQUISITION_COST_DOMINATES
MORPHOLOGY_LABEL_NOT_IDENTIFIABLE
CANNOT_CHECK_<reason>
```

## 12. Positive but scoped terminal

Only after prospective prediction + disjoint replication:

```text
DEVELOPMENTAL_GEOMETRY_PHASE_PREDICTION_SUPPORTED_AT_REGISTERED_SCOPE
```

This still does not prove a general machine-intelligence theory.

## 13. Upgrade path

If the first family study works:

1. disjoint task-family replication;
2. replace one synthetic family with formal math/coding domain where exact verifier exists;
3. test whether the same geometry variables predict the transition;
4. only then use #221/#220 neutral morphology search to seek a predicted missing form.

## 14. Pre-registration rule

No confirmatory run until:

- task generator/version;
- family implementations/hyperparameter policy;
- meta-training data/order;
- resource meters;
- primary phase predictions;
- mediators;
- exclusions/timeouts;
- negative terminals

are all frozen.
