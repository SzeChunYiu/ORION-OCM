# Why finite micro-derivation is scientifically weak v1

Status: **programme correction / no-go against overinterpreting Stage-D toy derivations**.

## Problem

Track B originally planned to derive one tiny example each of:

```text
neural
symbolic/production
probabilistic
programmatic
```

from the same frozen low-level basis.

That remains useful as a compiler sanity check, but it cannot carry the central claim.

## Finite flattening problem

If a target system has finite internal/configuration state and is evaluated over finite histories, its complete registered behavior/update trajectory can be encoded by a finite transducer or lookup table.

Therefore a generic finite-state/program parent can always pass a sufficiently tiny D0 representability assay, even if it destroys the target morphology's natural factorization.

So:

```text
tiny target compiled successfully
```

is mostly evidence that the basis/program language can represent a finite function/state machine.

It is not evidence for a deep common intelligence substrate.

## Stage D must become a family/scaling test

Keep tiny instances only as exact base cases. The scientifically meaningful question is whether **families** of increasingly large target morphologies compile with controlled developmental/resource overhead while preserving the natural update law.

For each target family `M_n`, register a size/complexity parameter `n` and compare:

```text
description size
execution work
update / learning work
communication
state touched by local update
compiler/search work
verification
```

as `n` grows.

Candidate target families:

### Neural/differentiable family

- width/depth `n`;
- finite-precision affine/nonlinear units;
- one or more registered parameter-update rules;
- compare natural factorized execution/update against flat/program emulation.

### Symbolic/production family

- rule count / predicate width `n`;
- sparse firing/rete-like or indexed parent where appropriate;
- registered rule-learning/chunking update.

### Probabilistic family

- variable/factor count `n`;
- explicit stochastic or exact rational finite model;
- conditioning/inference update;
- compare factorization vs flattened joint-state parent.

### Programmatic/library family

- program/library size `n`;
- repeated substructure/reuse;
- synthesis/library update;
- compare explicit library factorization vs inlined/flat representation.

## Bounded developmental compilation target

A target family supports a nontrivial D1 result only if there exists a compiler from the shared basis such that, over the registered scale family,

\[
R_B(M_n) \le f(R_{native}(M_n))
\]

for a prospectively declared overhead class `f` (e.g. constant-factor, linear, polynomial), **and** the same relation holds for the registered update/development operation, not only inference.

A one-off finite table does not satisfy this requirement if its size/work grows exponentially relative to the native factorization.

## Strong parent attack

For every family compare against:

- the native mature implementation;
- a general program/compiler representation;
- the strongest known factored conventional parent;
- a deliberately flattened finite-state/table representation only as a lower-quality calibration, never the headline parent.

## Important possible outcomes

```text
CROSS_PARADIGM_BOUNDED_COMPILATION_SUPPORTED_AT_SCOPE
NATIVE_FACTORIZATION_RESOURCE_IRREDUCIBLE_AT_SCOPE
GENERAL_PROGRAM_PARENT_SUFFICIENT
FLATTENING_EXPONENTIAL_BUT_PROGRAM_PARENT_COMPACT
NO_COMMON_BASIS_WITH_ACCEPTABLE_OVERHEAD
```

## Consequence

Stage D should no longer ask mainly:

> Can the basis produce one small neural/symbolic/probabilistic/programmatic object?

It should ask:

> Does one frozen low-level basis preserve the *scaling structure and developmental update economics* of several morphology families without hiding architecture-specific macros?

Only the latter materially informs the general-machine-intelligence hypothesis.
